# ADR-001: SQLite as the storage engine

## Status

Accepted

## Date

2026-09-20

## Context

A service keeps configuration, counters, and a processing position in one JSON file that it rewrites in
full on every change. It restarts several times a day (deploys, OOM kills) and has already come back with
an emptied file, losing all state. The contract it must honour: once it answers "gravei", the value must
survive a restart, whatever happens.

Constraints: Python standard library only; a `python -m kvstore` CLI with `set`/`get`/`del`/`list`; text
values that can be large; a number of keys and writes that grows forever with nobody cleaning up; the
state directory belongs exclusively to this store.

The failure mechanism is worth naming precisely, because it drives the decision: rewriting the whole file
puts the *entire* dataset at risk on *every* write. Any design where a single interrupted operation can
truncate or replace all of the data reproduces the incident, no matter how careful the rest of it is.

## Decision

Store the data in a single SQLite database (`kvstore.db`) inside the state directory, using the standard
library's `sqlite3` module, in WAL journal mode, with one table `kv(k TEXT PRIMARY KEY, v BLOB NOT NULL)`
and one autocommitted transaction per mutation.

## Alternatives Considered

### Alternative 1: Append-only log with an in-memory index (bitcask-style)

- **Description**: append length-prefixed, CRC-tagged records to `data.log`, fsync before acking, rebuild
  a key→offset index by scanning the log at open, truncate a torn tail during recovery, exclude concurrent
  writers with an `flock` lock file, and compact the log into a new file with `os.replace` when dead bytes
  exceed a threshold.
- **Pros**: no dependency beyond `os`/`struct`/`zlib`; append-only writes are conceptually simple; the
  durability point (fsync before ack) is explicit and easy to read in the code.
- **Cons**: it is four mechanisms, not one — record framing and checksums, crash recovery with tail
  truncation, multi-process locking, and a compactor with its own atomic-rename crash window. Each is a
  place a durability bug can hide, and each needs its own fault-injection tests. Subtleties that bite:
  a reader must never truncate a torn tail (only the lock holder may), a mid-file CRC failure silently
  ends the log and hides every good record after it, and compaction must not strand a concurrent reader.
  Index rebuild time and memory scale with the live key count.
- **Why rejected**: it hand-writes what SQLite already implements and has had tested for two decades, and
  it does so in exactly the area where this project cannot afford to be wrong. "Standard library only"
  does not mean "write the storage engine yourself" — `sqlite3` *is* the standard library.

### Alternative 2: Whole-file rewrite made atomic (`tmp` + `os.replace` + fsync)

- **Description**: keep the JSON file, but write a temporary file, fsync it, `os.replace` it over the
  original, and fsync the directory.
- **Pros**: the smallest possible change to the current code; `os.replace` is atomic on POSIX, so the
  file is never observed half-written, which does fix the emptied-file incident.
- **Cons**: every `set` costs a serialization and rewrite of the entire dataset plus an fsync of the whole
  file. The requirement says keys and writes grow forever and values can be large, so the per-write cost
  grows without bound. It also keeps two full copies on disk at peak, and holds the whole dataset in
  memory on every write.
- **Why rejected**: it fixes the crash safety but not the growth; the cost per write is proportional to
  total state, which the requester explicitly said grows forever.

### Alternative 3: `dbm` (`dbm.gnu` / `dbm.ndbm` / `dbm.dumb`)

- **Description**: use the standard library's key-value mapping over a DBM file.
- **Pros**: it is stdlib, the API is a dict, and it is the shortest code of all the options.
- **Cons**: no durability contract — `dbm.gnu` syncs only when asked and its crash behavior is
  unspecified, `dbm.dumb` is documented as not crash-resistant and can be corrupted by an interrupted
  write, and which implementation you actually get depends on the build. No multi-process safety.
- **Why rejected**: the single hard requirement is "acked writes survive a crash", and `dbm` does not
  offer that guarantee under any of its backends.

### Alternative 4: One file per key on the filesystem

- **Description**: each key is a file; `set` writes a temp file, fsyncs, renames; `del` unlinks; `list`
  reads the directory.
- **Pros**: trivially correct per key, no index, unbounded value sizes, and the blast radius of a write is
  one key.
- **Cons**: keys must be escaped into safe filenames (and un-escaped for `list`), a directory with
  millions of entries degrades and is painful to operate, and each write costs a file creation plus two
  fsyncs (file and directory).
- **Why rejected**: the unbounded key growth makes the directory itself the scaling problem, and filename
  escaping adds a correctness surface for no benefit over SQLite.

## Consequences

### Positive

- Crash safety, automatic recovery on open, multi-process serialization, and free-page reuse arrive as one
  well-tested mechanism instead of four hand-written ones.
- A write costs work proportional to the value, not to the dataset: no full rewrite, ever, which removes
  the incident's mechanism entirely.
- The implementation is small enough to read in one sitting, which is itself a durability property.
- Concurrent CLI invocations against the same directory are safe by construction.
- The operator can inspect and repair state with the `sqlite3` shell when the CLI is not enough.

### Negative

- The on-disk format is no longer human-readable; `cat` on the state file stops being a debugging tool.
- The directory holds three files (`kvstore.db`, `-wal`, `-shm`) instead of one, and copying the state
  means copying all of them (or running a SQLite backup).
- SQLite's behavior on network filesystems is poor; the directory must be on a local filesystem.

### Risks

- **Pragmas are per-connection and easy to lose**: `synchronous=FULL` must be re-applied on every open, and
  `auto_vacuum` only takes effect before the schema exists. Mitigation: both are asserted by tests
  (UT-018, UT-019, UT-030) rather than trusted to review.
- **Version skew in the on-disk format**: mitigated by `PRAGMA user_version` and an explicit refusal to
  open a newer format.

## Implementation Notes

- Connection order on a fresh database matters: `auto_vacuum=INCREMENTAL`, then `journal_mode=WAL`, then
  `synchronous=FULL`, then `busy_timeout`, then `CREATE TABLE IF NOT EXISTS`.
- Use `isolation_level=None` rather than the 3.12+ `autocommit=True` keyword, to keep the README's Python
  3.11+ floor.
- Use a plain rowid table, not `WITHOUT ROWID`: values are expected to be large, and `WITHOUT ROWID` is
  recommended against for large rows.
- Store the value as a BLOB of UTF-8 bytes so the round-trip is byte-exact.
