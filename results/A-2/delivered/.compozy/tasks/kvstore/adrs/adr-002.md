# ADR-002: Durability by `synchronous=FULL` and one transaction per mutation

## Status

Accepted

## Date

2026-09-20

## Context

[ADR-001](adr-001.md) settles *where* the data lives. This one settles *when a write is allowed to be
called done*, which is the actual requirement: "when the service answers 'gravei' to its caller, it has to
be there after the restart, whatever happens."

SQLite in WAL mode offers a choice of durability levels:

- `synchronous=OFF` — no fsync; a process crash is survivable, a power loss is not, and neither is a
  filesystem-level failure mid-commit.
- `synchronous=NORMAL` — the WAL is fsynced at checkpoints, not on every commit. A *process* crash (OOM
  kill, `kill -9`) loses nothing, because the data is already in the OS page cache and the OS survives the
  process. A power loss or kernel panic can lose the most recent committed transactions.
- `synchronous=FULL` — the WAL, including the commit frame, is fsynced before the commit returns. A
  committed transaction survives anything short of a storage-hardware failure.

The two failure modes actually observed are deploy restarts and OOM kills, both of which `NORMAL` already
covers, at roughly the cost of no fsync at all. The stated requirement, however, is unconditional.

There is a second, independent question: transaction granularity. Python's `sqlite3` with the default
`isolation_level=""` opens an implicit transaction on DML and holds it until an explicit `commit()`, which
means a caller who forgets to commit gets a silent, durable-looking write that is not durable — and a
process killed before the commit loses acked-looking work.

## Decision

Run every connection with `PRAGMA synchronous=FULL` in WAL mode, and make every mutation its own
autocommitted transaction by opening the connection with `isolation_level=None`. `Store.set` and
`Store.delete` return, and the CLI exits 0, only after that transaction has committed.

kvstore performs no write buffering, no batching, and no deferred flush of its own.

## Alternatives Considered

### Alternative 1: `synchronous=NORMAL` in WAL mode

- **Description**: fsync the WAL at checkpoints rather than at each commit.
- **Pros**: far cheaper per write — roughly the cost of a memory copy instead of a disk flush, which for
  a write-heavy service is the difference between hundreds and tens of thousands of writes per second.
  Covers both failure modes actually seen (deploy restart, OOM kill).
- **Cons**: a power loss or kernel panic can lose recently committed transactions, which contradicts an
  explicit, unconditional requirement. It also makes the guarantee conditional on a distinction the
  service's callers cannot see: "your write survives a crash, but a different kind of crash loses it."
- **Why rejected**: the requirement is "aconteça o que aconteça", and the caller's promise is what is
  being sold. Latency is the price of that promise, and the workload (configuration, counters, a
  processing position) is nowhere near a rate where the fsync cost matters.

### Alternative 2: Batch several writes into one transaction, flush periodically

- **Description**: accumulate writes and commit on a timer or a count threshold.
- **Pros**: amortizes the fsync across many writes; the standard throughput trick.
- **Cons**: it breaks the one thing being built. Between the write and the flush there is a window in
  which the caller has been told "gravei" and the data is not on disk — exactly the state the incident
  came from, just narrower.
- **Why rejected**: the ack is the product. Any buffering makes it a lie.

### Alternative 3: Expose the durability level as a caller option

- **Description**: a `Store(durable=False)` fast path for callers that do not need the guarantee.
- **Pros**: lets a future high-rate caller opt out without a redesign.
- **Cons**: speculative — no such caller exists — and it doubles the durability contract into two modes
  that every test, every doc line, and every incident postmortem must then distinguish.
- **Why rejected**: YAGNI. The pragma is one line; the option can be added the day a measured workload
  needs it.

## Consequences

### Positive

- The ack means exactly one thing, unconditionally, and it is the thing the service promises its callers.
- Crash recovery needs no kvstore code: the next open replays the WAL.
- Per-mutation transactions mean an interrupted process can never leave a half-applied multi-write state,
  because there is no multi-write state.
- `isolation_level=None` removes the whole class of "forgot to commit" bugs.

### Negative

- One fsync per write sets the write-rate ceiling — on ordinary hardware, order-of-hundreds of writes per
  second, not thousands.
- No multi-key atomicity: two related keys can be observed mid-update between their two writes. Recorded
  as a Non-Goal in the spec.

### Risks

- **The pragma is per-connection and silently defaults back** to `NORMAL`-or-whatever if an open path
  forgets it, and nothing about the store's behavior looks different afterwards. Mitigation: UT-018 and
  UT-019 assert `PRAGMA synchronous` and `PRAGMA journal_mode` on a live connection, so a regression fails
  the suite rather than the next incident.
- **fsync-per-write on a slow or contended disk** turns into caller latency. Mitigation: the workload is
  low-rate by description; if that changes, the option in Alternative 3 becomes justified, and the
  measurement — not the guess — is what justifies it.
- **Power-loss durability cannot be proven by this test suite.** It is inherited from SQLite's guarantee,
  and what the tests verify is the configuration that guarantee depends on, plus direct process-kill
  tests. This limit is stated in `_tests.md` rather than papered over.

## Implementation Notes

- `PRAGMA synchronous=FULL` must be executed on *every* connection, immediately after connect; unlike
  `journal_mode`, it is not persisted in the database file.
- `PRAGMA busy_timeout` (or `sqlite3.connect(timeout=...)`) covers writer contention; it is independent of
  durability and is set alongside it.
- Nothing in `Store` may hold an open transaction across a return to its caller.
