# ADR-002: Índice em sqlite3 com tabela invertida própria

## Status

Accepted

## Date

2026-09-20

## Context

O índice precisa: sobreviver entre execuções do cron; responder "em quais arquivos este termo aparece" sem
varrer a pasta; ser atualizado parcialmente (só os arquivos alterados, ADR-001); e não ser corrompido por
uma execução interrompida no meio. A restrição do enunciado é dura: **só biblioteca padrão do Python**.

## Decision

O índice é um arquivo sqlite3 em `<diretorio>/.fidx.sqlite3`, com três tabelas e uma tabela invertida
escrita à mão:

```sql
CREATE TABLE meta     (chave TEXT PRIMARY KEY, valor TEXT);          -- schema_version
CREATE TABLE arquivos (caminho TEXT PRIMARY KEY, digest TEXT NOT NULL);
CREATE TABLE termos   (termo TEXT NOT NULL, caminho TEXT NOT NULL, PRIMARY KEY (termo, caminho));
CREATE INDEX termos_caminho ON termos(caminho);                      -- apagar por arquivo
```

A busca é `SELECT caminho FROM termos WHERE termo = ?`, com interseção entre os termos da consulta.
FTS5 não é usado. `PRAGMA journal_mode=WAL` na criação, para que um `search` responda enquanto um `index`
escreve. A execução do `index` inteira acontece em **uma transação**.

O arquivo do índice mora **dentro** do diretório indexado, e é ignorado pela varredura por já cair na regra
de "entradas que começam com ponto" (mesma regra que exclui `.git/`).

## Alternatives Considered

### Alternative 1: sqlite3 FTS5

- **Description**: `CREATE VIRTUAL TABLE ... USING fts5(conteudo, caminho UNINDEXED)`.
- **Pros**: tokenização, ranking (`bm25`), busca por prefixo e por frase de graça; menos código nosso.
- **Cons**: FTS5 é opção de compilação do sqlite — está presente no CPython desta máquina, mas não é
  garantido em toda build (distros já entregaram sqlite sem ele), e a falha aparece só em tempo de execução,
  no cron, num `sqlite3.OperationalError: no such module: fts5`. Traz junto uma tokenização que não é a
  nossa e guarda o conteúdo completo dos arquivos dentro do índice.
- **Why rejected**: o requisito é só "quais arquivos contêm o termo" — sem ranking, sem frase, sem trecho.
  Pagar uma dependência de build condicional por recurso que não foi pedido não se justifica; a tabela
  invertida própria é ~20 linhas e roda em qualquer build.

### Alternative 2: JSON / pickle com o dicionário invertido em memória

- **Description**: `{termo: [caminhos]}` serializado a cada rodada.
- **Pros**: trivial de escrever e inspecionar.
- **Cons**: carrega o índice inteiro na memória para qualquer busca; reescreve o arquivo inteiro a cada
  rodada — o que anula o incremental da ADR-001 justamente na parte cara (a escrita); e a reescrita não é
  atômica sem trabalho extra (`tmp` + `os.replace`). `pickle` ainda adiciona a superfície de executar código
  ao carregar um arquivo que chega por rsync.
- **Why rejected**: contradiz o objetivo (não reprocessar/reescrever o que não mudou).

### Alternative 3: índice fora do diretório (`~/.cache/fidx/<hash-do-caminho>.sqlite3`)

- **Description**: manter a pasta indexada intocada.
- **Pros**: funciona em pasta somente-leitura; nenhum artefato nosso entra no rsync ou no `git status`.
- **Cons**: índice órfão quando a pasta é movida ou apagada; menos óbvio de inspecionar e de apagar;
  precisa de uma regra de nomeação para não colidir entre pastas.
- **Why rejected**: por ora, o padrão previsível vence — o índice ao lado do que ele indexa, apagável com um
  `rm`. Se aparecer pasta somente-leitura, isto vira um flag `--index <caminho>` sem mudar o formato.

## Consequences

### Positive

- Atualização parcial real: apagar e regravar as linhas de um único arquivo é uma operação barata.
- Uma transação por execução dá a garantia de US-003.EC-4 de graça — `index` interrompido não deixa índice
  pela metade; o rollback devolve o estado da última rodada boa.
- O bloqueio do sqlite dá o comportamento de US-003.EC-3 sem lockfile nosso: a segunda execução simultânea
  bate em `database is locked`, que viramos em mensagem e saída 2.
- Sem FTS5, o mesmo código roda em qualquer build de CPython da máquina do operador.

### Negative

- Tokenização, normalização de caixa e interseção de termos passam a ser código nosso (pequeno, mas nosso) —
  e com isso a semântica de busca é por palavra inteira, diferente do `grep` que o operador usa hoje.
- O arquivo `.fidx.sqlite3` aparece dentro da pasta indexada; quem versiona a pasta precisa ignorá-lo.

### Risks

- `meta.schema_version` divergente (índice de uma versão anterior do fidx) → o índice é descartado e
  reconstruído do zero. É o caminho seguro; custa uma rodada completa e está coberto por US-003.EC-2.
- Crescimento da tabela `termos` em pasta com muitos termos únicos. Ceiling conhecido, aceito: ainda é
  ordens de grandeza menor que o conteúdo, e o `search` vai no índice do `PRIMARY KEY (termo, caminho)`.

## Implementation Notes

- `sqlite3.connect(caminho, isolation_level=None)` e controle explícito de `BEGIN IMMEDIATE` / `COMMIT` no
  `index`, para que o bloqueio de escrita apareça no início e não no meio da varredura.
- `timeout` curto na conexão do `index` (o padrão é 5 s): a segunda execução do cron deve falhar rápido e
  sair, não enfileirar.
- Reprocessar um arquivo é `DELETE FROM termos WHERE caminho = ?` seguido de `executemany` do conjunto novo.
